zkAPI escrows ETH on Ethereum and uses zero-knowledge proofs to authorize API usage without revealing which deposit pays for it. The deployed integration issues bounded OpenRouter credentials through Open Anonymity. Prompts go to the inference provider, which can read them. **The deposit and its withdrawal are publicly linked by note id.** This is privacy for service authorization, rather than private transfers between Ethereum addresses.

### Funding and API usage

A deposit publishes its funding address, commitment, amount, sequential note id and expiry. The wallet generates a random note secret locally and proves membership in the active-note Merkle tree. The [request circuit](https://github.com/ethereum/zkapi/blob/045b444ea1b52538d1b40273c7cb6ed09468a052/protocol/rust/crates/zkapi-proof/src/groth16.rs#L368-L485) proves that the note has enough balance for a public spending bound. The note id, exact balance, expiry, secret and operator signature are private witnesses. A fresh note uses its deposited balance without needing an operator signature.

After usage, the operator signs a new balance commitment. The commitment binds the balance to the same note, while blinding hides its contents. The operator knows the charge and credential it issued. Proof validity establishes authorization and balance accounting, but does not establish that an API service was delivered or that its reported bill is correct. The client checks settlement against its authorized budget and pinned ETH/USD quote. The deployment's request cap is {{requestChargeCap}} ETH in whole-gwei units. It is a client/service pin, rather than an onchain comparison of every request's spending bound. [Billing implementation](https://github.com/ethereum/zkapi/blob/045b444ea1b52538d1b40273c7cb6ed09468a052/crates/zkapi-serverd/src/processor_v2.rs).

The live deployment uses Open Anonymity's credential issuer and production verifier, with inference sent to OpenRouter. The verifier receives the issued API key. Verifier approval does not prove that the inference provider refrains from logging prompts, responses or credentials. The local desktop client shares a credential across compatible requests within its default reuse window, including across chats and local clients. Disabling reuse requests fresh access for each inference request. [Client credential reuse and content boundaries](https://github.com/ethereum/zkapi/blob/045b444ea1b52538d1b40273c7cb6ed09468a052/zkapi-clientd/docs/PRIVACY.md).

### Withdrawals, disputes and expiry

A cooperative close requires a withdrawal proof and clearance signed by the pinned operator key. It reveals the original deposit's note id, remaining balance, payout address and nullifier. The vault sends the remaining balance to the destination and the difference from the original deposit to the treasury. Thus total consumption becomes public, even though individual API requests stay offchain.

An escape withdrawal requires a proof of the user's state and waits {{challengePeriod}}. Anyone holding a valid request proof with the same nullifier can challenge it before the deadline. The contract checks proof validity and deployment bindings, but does not check whether the operator accepted the request or delivered service. The challenge restores the note to the active tree and leaves that nullifier consumed. A user who submitted a request proof without receiving a successor state therefore depends on the operator's signature to resume ordinary spending or withdraw from the updated state if that proof is used to challenge. The escape path bypasses withdrawal clearance, but does not replace missing settlement evidence. [Vault exit and challenge logic](https://etherscan.io/address/0x4386FDbdA35D995beB3BF8625118Ec5982ec81fe#code).

Deposits expire after {{noteTtl}}, rounded up to a {{expiryBucket}} boundary. Anyone can then sweep the **entire active note** to the treasury, including its unused balance. Expiry is a competing sweep, rather than an automatic refund or an immediate prohibition on withdrawals. Starting an escape moves a note out of active status, protecting that pending withdrawal from the expiry sweep.

The owner can immediately pause deposits, cooperative closes and the initiation of new escapes. Challenges, already pending escape finalizations and expiry sweeps remain available. A malicious owner can keep the vault paused through expiry and redirect the sweep proceeds by changing the treasury. This is a confiscation path despite the fixed vault code and proof keys. A rejecting destination or treasury can also revert a payout because both ETH transfers must succeed.

### Privacy boundaries and client choices

The browser wallet stores note secrets and recovery journals on the device and generates proofs locally. It downloads the same [complete tree snapshot](https://github.com/ethereum/zkapi/blob/045b444ea1b52538d1b40273c7cb6ed09468a052/sdk/services/browserWalletRuntime.js#L829-L845) as other clients and derives its note's path locally. It does not send the note id to obtain that path. Direct service connections still expose IPs and timing. The hosted app's zkapi entrypoint disables its ordinary pageview analytics call, but the host and its deployment proxy can still observe requests. A frontend update can read the wallet's local secrets.

The desktop client's pinned Rust companion instead queries the [indexer by note id](https://github.com/ethereum/zkapi/blob/20aa542ae98e767c0507133fd34b12a56f5ccd3d/crates/zkapi-clientd/src/indexer.rs#L69-L104), including before authorizations. The operator running both indexer and API service can correlate these queries with API activity. The desktop offers a loopback SOCKS5/Tor or Wisp route for its Go transport, but its [Rust protocol transport](https://github.com/ethereum/zkapi/blob/045b444ea1b52538d1b40273c7cb6ed09468a052/zkapi-clientd/internal/zkapi/protocol-transport.patch#L23-L80) builds a separate HTTP client. Selecting the relay alone does not route every wallet request.

An inspected browser build using common snapshots and separate network identities for funding and API use avoids the desktop's direct note-path disclosure. Routing all application traffic through Tor addresses IP exposure. It does not enlarge the set of eligible notes, conceal identifying prompts or remove the provider's access to its API credential and content. A custom Ethereum RPC requires a reviewed profile and matching deployment manifest because the browser checks the RPC against a packaged pin. These are integration changes, rather than a hosted wallet settings switch.

An observer who receives an authorization proof can use its request time and spending bound alongside public deposit amounts and expiries to narrow the eligible notes. These inputs remain offchain during ordinary API use. A small or unique eligible set can defeat authorization anonymity even with a correct proof. Publishing a challenge reveals a submitted authorization and associates its nullifier with the public note. The project's anonymity-set chart is therefore disabled: a count of funding addresses would imply deposit-to-withdrawal protection that the contract does not provide.

### Cryptography and availability

The protocol uses Groth16 over BN254, Poseidon hashing and note-bound Baby-JubJub commitments and Schnorr signatures. The published keys were generated in a [single-party setup](https://github.com/ethereum/zkapi/blob/045b444ea1b52538d1b40273c7cb6ed09468a052/protocol/setup/v2/README.md). Retained setup secrets can permit forged proofs. Matching public artifacts and deployed source cannot establish that these secrets were destroyed.

Withdrawal clearance and non-genesis settlement depend on fixed signing keys. The holder cannot be replaced within this vault. The indexer can be reconstructed from Ethereum events, but substituting a new operator cannot manufacture signatures under the pinned keys. API usage additionally depends on the credential issuer, verifier and inference provider. Losing local secrets or unresolved recovery journals can make funds unrecoverable.

The signature and proof systems are not post-quantum. A future attacker breaking elliptic-curve cryptography can forge signatures and compromise soundness. This does not automatically recover every historical secret from the randomized commitments. Chain-visible deposit and withdrawal links are already permanent, while service logs and retained prompts create their own future disclosure path.

Flow statistics count deposits and actual user payouts from cooperative and finalized escape withdrawals. They exclude escape initiation, cancelled escapes, treasury consumption shares and expiry sweeps. TVS measures the vault's whole ETH balance, which also contains operator revenue awaiting note closure.
