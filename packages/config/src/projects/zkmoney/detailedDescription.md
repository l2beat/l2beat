zk.money is a private payments wallet for DAI by Aztec Labs. Funds are escrowed in the ZkMoneyPortal on Ethereum and held as private notes of the zk.money token contract on the Aztec Network, where users pay each other by tag (a zk.money name).

### Deposits
Users deposit to one-time deposit addresses (SIPAs) derived for their account. Anyone can sweep a funded deposit address into the portal: USDC and USDT are swapped to DAI through the Curve 3pool, the sweeper receives {{depositFee}} ({{registrationSweepFee}} for the deposit that claims a tag) and the rest is sent to Aztec through the canonical Inbox. Claiming a tag costs {{registrationFee}} by default including that sweep fee, paid from the first deposit. The domain owner can sign custom prices, but the registration fee must cover the {{registrationSweepFee}} sweep fee. The portal accepts at most {{depositLimit}} per {{depositRefillTime}}, and every deposit, payment and withdrawal is capped per transaction.

### Multi-proof system
Every payment and withdrawal needs, in addition to the zk validity proof of the L2, a signature from an AWS Nitro enclave registered on the portal (2/2). Anyone can register an enclave with a fresh AWS attestation of the one approved image. Aztec Labs publishes that image, but not its build, so nobody can check that it runs the published enclave code. Stealing funds requires a failure of Aztec's private execution and of the enclave layer at the same time. But every exit depends on a live enclave, and enclaves see every operation in plaintext.

### Fees
The portal takes {{fpcFundingCut}} from every deposit and withdrawal to fund a fee-paying contract that pays the Aztec fees of zk.money users, and anyone can refill it. It only sponsors accounts whose tag the domain owner signed, or that got a voucher from such an account. The wallet offers no other way to pay fees, so transactions wait while that contract is empty or Aztec fees exceed what it pays. The account contract can also pay with its own Fee Juice, but only modified wallet code uses that.

### Tags, resolver and passkeys
- **Tags** are registered on Ethereum together with the account's Aztec address and keys, so anyone who knows a tag can look up the account behind it. Every claim needs a signature from the domain owner, which zk.money's closed-source claim server gives only for names outside its blocklist, and there is no way around it. Without a tag, the released wallet can neither pay fees nor restore the account on a new device.
- **The resolver** is only needed for payments to name.zk.money from outside zk.money, for example from MetaMask. The Resolver contract asks the recipient's resolver operator for a fresh deposit address and checks its zk proof. Payments inside zk.money and deposit addresses the wallet creates itself read the registry on Ethereum and work without it. Users can switch their operator and anyone can register one, but the only operator is Aztec Labs' closed-source service, and the circuit behind the proof is not published.
- **Passkeys** belong to auth.zk.money, which has to list wallet.zk.money before the browser lets the hosted wallet or zk.money Desktop use them, on every use. The contracts do not check where a passkey signature comes from, so a wallet served under auth.zk.money itself does not need that list. Whoever controls the zk.money domain controls where the passkeys work.

### Compliance
The contracts on Ethereum and Aztec and the enclave check no address lists. They only enforce validity, the per-transaction cap and the deposit rate limit. The checks are in the wallet and in the services Aztec Labs runs, besides the name blocklist:

- **Wallet:** before a deposit from a connected wallet, a withdrawal, a payment-link claim to Ethereum or a deposit address recovery, the wallet sends the Ethereum address involved to Predicate through zk.money and stops if Predicate flags it or cannot be reached. Paying a deposit address by hand from another wallet skips this check.
- **Relayer:** before it submits an L1 operation such as a sweep, a withdrawal or a refund, it simulates it and checks the target and every sender and receiver of a token transfer against the OFAC SDN list, and against Predicate if configured. A hit blocks the operation.
- **Resolver:** before it announces a payment to a zk.money name, it checks the deposit address and the addresses that funded it against the OFAC SDN list. A hit means the payment is never announced to the recipient nor swept, and only the recipient can recover it, with own tooling that re-derives the deposit address.

A censored user can sweep a funded deposit address and finalize a proven withdrawal on Ethereum themselves, and the wallet offers both. A withdrawal still needs an enclave signature, but the enclave screens nothing. The wallet's checks apply per address, so another address or a modified desktop build gets past them.

### Setups
- **Hosted web wallet:** its code is loaded from zk.money on every visit, so whoever controls the zk.money domain or its web deployment can serve code that reads all of a user's keys except the spending key and gets any operation signed, since the passkey prompt does not show what is being signed. By default it uses an Aztec node run by Aztec Labs and an Ethereum RPC chosen by zk.money. Users can replace both, and the enclave, in the settings.
- **zk.money Desktop with own Aztec node and Ethereum RPC:** it serves the wallet from the user's computer, built from the published source by the repository's release workflow, so its code cannot change underneath the user. It still needs zk.money online: it loads the contract addresses on every start from two unsigned lists run by Aztec Labs (the config profile, with the copy baked into the release as a fallback, and the Oxide deployment manifest, without one), screens addresses through zk.money and uses the passkey through the auth.zk.money list.
- **Modified desktop build:** served under auth.zk.money, with its own copies of the two lists and without the Predicate check, it needs no zk.money service and is only constrained by the immutable contracts. It can sweep deposits and finalize withdrawals itself with ETH, and use an enclave the user runs on AWS. Its remaining dependencies on Aztec Labs are the enclave image, which only Aztec Labs publishes, and the domain owner signature for new tags. L2BEAT did not run such a build.

In every setup the wallet keeps the master key, from which all keys except the spending key derive, unencrypted in the browser profile until the user signs out, and the viewing keys and decrypted notes until the user clears the wallet's local data, so anyone with access to the device can read the user's whole history. The enclave sees every operation and must sign every exit, and the resolver operator can link deposits to their recipients.
