# Architecture

The deBridge Liquidity Network (DLN) is an intent protocol built on top of the deBridge messaging protocol, sharing its validation layer and governance. Users (*makers*) create cross-chain orders by locking their *give* funds directly in the `DlnSource` contract on the source chain — there is no separate vault, and maker principal can only leave through a validated cross-chain message or a contract upgrade. On the destination chain, *takers* fulfill orders through the `DlnDestination` contract by paying the *take* amount, which is forwarded to the recipient within the same transaction, so `DlnDestination` holds no user funds. Orders can also target Solana (per-chain *engine* configuration). A protocol fee (currently 0.001 ETH flat plus 4 bps on Ethereum, refunded on cancellation) is deducted from the give amount at order creation; the recorded maker is `tx.origin`, while tokens are pulled from the calling contract.

# Order lifecycle

Fulfillment is permissionless — anyone can fill any order unless the maker restricted it via `allowedTakerDst` — and the filler names an *unlock authority* for the order. Only that unlock authority can later trigger the unlock, which sends a message (batchable, up to 50 orders per batch to EVM chains) back to the source chain's `DlnSource` through the `DeBridgeGate`; the taker attaches native tokens to cover the messaging fee plus an optional execution fee for the relayer who lands the claim on the source chain. Once the deBridge validators attest the message, the escrowed give funds are released to the taker's chosen beneficiary. Fulfilled state is tracked per order ID, which commits to all order parameters including a hash of any attached calldata.

# Crosschain validation

`DlnSource` releases escrowed funds only to calls from the deBridge `CallProxy` whose authenticated original sender is the `DlnDestination` address configured for the order's destination chain (an admin-set, event-tracked map currently covering 37 chains). The authenticity of that claim rests entirely on the deBridge validator set: a quorum of validator signatures (currently 8 of 12 on Ethereum) attests each unlock or cancellation message. A compromised validator quorum, or an admin change of the per-chain routing addresses, allows draining all order funds escrowed in `DlnSource`. As a defense in depth, an unlock whose authenticated source chain does not match the order's destination chain is silently ignored rather than paid out; a cancellation with the same mismatch reverts. Some failure states have no onchain recovery path: claims arriving for orders in an unexpected state are only recorded (no function pays them out), and a chain-ID-mismatch unlock burns the destination-side order status, so resolving either requires an upgrade or offchain intervention by the operators.

# User recovery

Unfilled orders can be cancelled from the destination chain by the maker-designated order authority, refunding the full escrow including all fees to the maker on the source chain. A `GOVERNANCE_DELEGATED_ORDER_CANCEL_ROLE` — held on Ethereum by an EOA delegated (EIP-7702) to a smart wallet — can force-cancel unfulfilled orders on behalf of makers, but only for orders that pre-committed a cancel beneficiary, and refunds can only go to that maker-designated address, making it a liveness rather than a theft power. Fulfilled orders cannot be cancelled.

# External calls

Orders can carry calldata to be executed on the destination chain after fulfillment. In that case the taker's funds are routed to an `ExternalCallAdapter` escrow, which releases them when the registered executor contract runs the calldata (the filler can claim an execution reward) or refunds the order authority on cancellation. The adapter is admin-replaceable in `DlnDestination`, so a malicious adapter could steal the funds of every order carrying calldata; the currently registered `ExternalCallExecutor` has unverified source code.

# Intents

A newer intent-manager stack automates order creation: users sign an EIP-712 *intent* offchain — note the signature covers only an opaque 32-byte intent hash, so wallets cannot display the actual constraints — and permissionless fillers turn intents into DLN orders through the `DeBridgeIntentManager`. There is no signature nonce; replay is bounded only by the per-intent budget accounting, so an intent is multi-fill until its budget is exhausted, expired, cancelled or nullified (users, and a governance role globally, can nullify by timestamp). Input tokens are pulled through the `DeBridgeAllowanceHolder`, the single immutable contract holding all user approvals of the intent system: its transfer functions carry no intent-level checks, so any holder of its `ALLOWED_SPENDER_ROLE` can move any approved token from any approver to any recipient. All user protection lives in the constraints of the signed intent itself (price bounds, allowed senders, receivers, budgets); the fill fee is *not* part of the signed intent and is set by the intent manager admin (up to 100%, effective immediately — on the same-chain path it is deducted after the user's minimum-output check). The contract is otherwise non-custodial: tokens move from the user to the DLN escrow within the fill transaction.

# Upgradeability and governance

`DlnSource` (which escrows all in-flight maker funds), `DlnDestination` and the `ExternalCallAdapter` are transparent upgradeable proxies whose `ProxyAdmin` is owned by the same 5/8 deBridge multisig that governs the messaging protocol, with no timelock or exit window. The multisig also holds the `DEFAULT_ADMIN_ROLE` on both DLN contracts, controlling the trusted cross-chain routing addresses, fees (no upper bound; a fee near 100% would confiscate new orders' give amounts), the external call adapter, and unpausing. The intent-manager stack has a weaker setup: on Ethereum, a single EOA is simultaneously the admin of `DeBridgeIntentManager` and `DeBridgeAllowanceHolder` and the owner of the (unverified) ProxyAdmin that can upgrade the intent manager — an upgrade there could abuse the allowance holder's spender role to drain all outstanding user approvals. Several satellite contracts (including the `ExternalCallExecutor`) have unverified source code.

# Monitoring

Order creation, fulfillment, unlock and cancellation all emit events, and the per-chain routing configuration (`SetDlnDestinationAddress`/`SetDlnSourceAddress`) is event-tracked by L2BEAT's discovery. deBridge provides an [explorer](https://app.debridge.finance/explorer) (DLN trades are labeled as such) for tracking order flow.
