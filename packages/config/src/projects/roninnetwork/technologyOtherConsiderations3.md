Since 2026-09-07 (block 25924899, tx `0x7f1b7013…cded482`) the respected game type is again the PermissionedDisputeGame (type 1): the RoninConduitOwner Safe, acting as Guardian, called `setRespectedGameType(1)` on the AnchorStateRegistry, moving withdrawals off the Kailua ZK game (type 1337) that had been respected since 2026-07-01. The Kailua contracts (KailuaGame implementation, KailuaTreasury, KailuaVerifier and the RISC Zero verifier set) remain deployed and `game1337` is still registered in the DisputeGameFactory, but new Kailua proposals stopped on 2026-09-07 and any Kailua game created from now on would not be respected for withdrawals; Kailua games created before the flip stay valid once resolved. No public announcement explaining the change or stating whether it is temporary was found.

The permissioned games commit to the op-program v1.3.1 prestate (`0x038512e0…6764d54c`). That binary embeds the superchain-registry snapshot at commit 42bd03ba8313 (2024-08-21), which lists 17 chain IDs and does not include Ronin (chain ID 2020); it also predates Ronin's custom gas token and EigenDA derivation. If a dispute game were stepped through to the VM, op-program's `RollupConfigByChainID(2020)` would not find a rollup config and would panic, producing an invalid output state, so any claim (honest or fraudulent) could be "disproven" against the panic. Only the permissioned proposer can create state proposals and only the proposer and challenger can move or step, so the proof system currently reduces to an operator-attested delay timer rather than an adversarial fraud proof. Fixing it requires redeploying games with a chain-specific prestate, or returning the respected game type to Kailua.
