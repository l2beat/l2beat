§1

Why this exists — the wipe mechanic

Every daTracking entry becomes a backend indexer configuration keyed by a content hash of its identity fields (createDaTrackingId, @l2beat/shared). The backend diffs stored configurations against the config by id only (mergeConfigurations.ts):

· id appears → new configuration, syncs from scratch.
· id disappears → configuration deleted, all its indexed data wiped.
· id kept but range edited → wipe + resync of that one config (DaIndexer has no trimData).

Stack templates used to derive the single tracking entry from current discovery values (discovered.json has no history). One on-chain batcher rotation ⇒ new identity ⇒ new id ⇒ the old era silently ceased to exist ⇒ wipe on deploy.

// the old failure, step by step
discovery run
  batcherHash: 0xOld… → 0xNew…

template re-derives daTracking
  [{ inbox, sequencers: [0xNew…] }]
  // the 0xOld… era is GONE from config

deploy
  id(0xOld era) not found
  → deleteConfigurations + wipeData
  // months of DA data destroyed

The snapshot guard (PR #12380) turned this into a CI failure. The era ledger turns it into a one-command, non-event.

§2

Identity: what is hashed, what is not

id = sha1( type + daLayer + 'v2' + identity fields [+ discriminator] ).slice(0, 12)

typehashed (identity — changing any of these re-keys the data)not hashed (freely editable in place*)
ethereuminbox · sequencers (sorted) · topics (sorted)sinceBlock / untilBlock (or timestamps for eigen-da).

*“freely” = no re-key, but any range edit still costs a wipe + resync of that config on deploy (§8).
celestianamespace
availappIds (sorted)
eigen-dacustomerId

The optional discriminator is new. It participates in the hash only when set, so every pre-existing production id is untouched. Its single purpose: give the third era of an A→B→A rotation a distinct id (§5·F5) — previously inexpressible, since two eras with identical identity fields collide on one id.

Inbox strings are hashed verbatim — zksync2's old eras use eth:-prefixed addresses and must never be normalized.

§3

Resolution order — the three sources

Every opStack / orbitStack / zkStack project funnels through one entry point — resolveDaTracking() in packages/config/src/templates/daTrackingHistory.ts. First match wins. (agglayer passes nonTemplateDaTracking through and derives nothing; non-template projects set daTracking directly and are outside this mechanism.)

1

nonTemplateDaTrackingmanual override

Full escape hatch, returned verbatim. For configs that can't be derived: custom topics (taiko), archived projects whose eras are all closed (arenaz), hand-maintained specials (base, optimism, …). If it's set, the file and the derivation are both ignored.

src/projects/<name>/daTracking.jsonthe era ledger

Committed, machine-maintained era store — written only by pnpm da:history, never by hand. Holds the full history: closed eras (with untilBlock + provenance metadata) chained to the one open era. This is what the backend actually consumes for these projects.

The trick that makes the guard cheap

The derivation always runs, even when the file wins — resolveDaTracking records { source, derived } per project in a registry filled as a side effect of evaluating the templates. The staleness guard and the generator just call getProjects() and read the registry; nobody has to rebuild templateVars.

§4

The era file & its invariants

{
  "eras": [
    {
      "type": "ethereum",
      "daLayer": "ethereum",
      "inbox": "0x00f9…EEd0",
      "sequencers": ["0x2b87…AC8c"],
      "sinceBlock": 21169100,
      "untilBlock": 24776391,   ← closed era
      "closed": {
        "reason": "sequencers changed",
        "observedAtTimestamp": 1784282781,
        "precision": "bracketed"
      }
    },
    {
      "type": "ethereum",
      "daLayer": "ethereum",
      "inbox": "0x00f9…EEd0",
      "sequencers": ["0x4782…894B"],
      "sinceBlock": 24776391    ← open era, no until
    }
  ]
}

closed is provenance only — stripped by eraToConfig() before the backend sees anything. precision ∈ bracketed (from discovery-run timestamps) · exact (reserved for a future event-scan mode) · manual (CLI flags).

Parser invariants — parseDaTrackingHistory()

Violating any of these throws at config build. The file is generator-written, so a violation means a hand edit or a generator bug:

I1eras is non-empty
I2closed era ⇒ has untilBlock ≥ sinceBlock and a closed block; open era ⇒ has neither
I3within a (type, daLayer) group: sinceBlock ascending, and only the last era may be open
I4no two eras share a configuration id — identical identity fields require a discriminator on the later era
I5same-identity eras (ignoring discriminator) must have strictly disjoint ranges — they'd match the same data and double-count the shared blocks

Note what is not an invariant: consecutive eras of different identities may overlap or share a boundary block. That's deliberate — it's what makes bracketed boundaries (§6) legal.

Schema covers ethereum / celestia / avail only. eigen-da is timestamp-based and never template-derived, so it cannot live in an era file — the generator rejects it.

§5

All flows

F1

New project (or DA tracking newly derivable)

trigger: new listing / DA mode switch to blobs·celestia·avail
  1. Project lands using a stack template; derivation produces an entry; no file exists → registry source = derived.
  2. Guard “every template-derived project has a history file” fails CI, naming the project.
  3. Author runs pnpm da:history <project> → init: file written with one open era, sinceBlock = the template-derived value (inbox deployment block / SystemConfig startBlock). No boundary resolution, no RPC needed.
  4. Snapshot regenerated (new id registered). Commit file + snapshot with the project PR.
ids: +1 new · data: syncs from scratch · human input: zero decisions
F2

Steady state

trigger: routine discovery refresh, nothing DA-relevant changed
  1. Template derivation matches the file's open era by identity (ranges are ignored in the comparison — derived sinceBlock is the deployment block, stored sinceBlock may be a later rotation boundary; that mismatch is expected and fine).
  2. Guard green. pnpm da:history would report “already up to date”. Nothing to do.
ids: unchanged · file: untouched — this is the whole point: discovery refreshes no longer touch DA tracking at all
F3

On-chain rotation, same layer — the main event

trigger: batcherHash / batchPosters / validatorsVTL / inbox rotates
  1. Discovery refresh updates discovered.json; the derivation now yields a new identity.
  2. Staleness guard fails: “daTracking history for X is out of date with discovery” — in the same PR as the discovery change, by construction.
  3. Author runs pnpm da:history <project> (needs ETHEREUM_RPC_URL in packages/config/.env).
  4. Old era gets untilBlock = block at the local discovery run's timestamp; new era opens with sinceBlock = block at main's discovery run timestamp (git show main:…/discovered.json) — the bracket, §6. closed.reason records what changed (e.g. "sequencers changed", "inbox 0xA → 0xB").
  5. Snapshot regenerated: additions only — the old id lives on inside the closed era. Commit discovery + file + snapshot together.
ids: +1 new, 0 removed · data: old era's history preserved forever; old config wiped+resynced once (range edit, §8) · human input: run one command
F4

Spurious flap / discovery revert

trigger: F3 happened, but the “rotation” was noise and the value came back
  1. Next refresh: derivation matches the previous era again, not the open one → staleness guard fails again.
  2. Author runs pnpm da:history <project> --drop-last: the flap era is deleted and the previous era of its group is reopened (untilBlock and closed removed).
  3. Snapshot regenerated (the flap id disappears — that removal is the explicit sign-off; its short-lived data is expendable).
the generator also nudges you here: appending an era whose identity repeats an earlier one prints “if the previous era was a spurious flap, revert with --drop-last instead”
F5

Genuine A → B → A

trigger: a value really rotated away and later rotated back
  1. F3 runs for A→B, then later for B→A.
  2. The generator sees the new era's identity equals era №1, so it stamps discriminator: "1" (count of prior same-identity eras) — distinct id, no collision (I4), and I5 verifies the two A-eras don't overlap.
  3. Both A-eras coexist with separate backend configurations; each syncs exactly its own range.
before this mechanism, a pause/resume of the same identity was inexpressible — it tripped the duplicate-id guard and the backend's assertUniqueConfigId
F6

Layer switch (e.g. ethereum blobs → celestia)

trigger: derivation moves to a different (type, daLayer) group
  1. Staleness guard fails (open-era identity set ≠ derived set).
  2. pnpm da:history <project>: the abandoned group's open era is closed (reason: "no longer derived from discovery"); a fresh era opens in the new group.
  3. Block numbers live on different chains, so no chaining across groups: the new era keeps the template-derived sinceBlock (the celestiaDa.sinceBlock template var), and closing the ethereum era resolves its boundary on ethereum as usual.
  4. If the abandoned layer isn't ethereum, automatic boundary resolution is refused → F7's manual flags.
the file now permanently documents both chapters: the ethereum chapter (closed) and the celestia chapter (open)
F7

Manual boundary

trigger: non-ethereum layer rotation · no RPC · no readable main ref

Automatic bracketing only works for ethereum/ethereum (timestamp→block via ETHEREUM_RPC_URL + main's discovered.json). Everything else — a celestia namespace change, avail appIds change, or a machine without RPC/git context — takes the boundary explicitly:

pnpm da:history <project> --since-block <n> --until-block <n>  # blocks on the DA layer's own chain
  1. Supply blocks bracketing the change on the era's chain (since = safely before, until = safely after; overlap is fine, gap is not).
  2. Era closes with precision: "manual"; single-project only, so a bad flag can't spray across the fleet.
celestia/avail identities are still manual template vars today (// TODO: update to value from discovery) — their rotations start with a human editing the var, so a manual boundary is consistent
F8

Manual override territory (and its orphans)

trigger: config not derivable — custom topics, archived, hand-maintained
  1. nonTemplateDaTracking set → file and derivation both ignored; the project is protected only by the classic snapshot guard.
  2. If a daTracking.json also exists (or belongs to a renamed/removed project), the orphan guard fails: a file nobody reads is a lie waiting to be believed. Delete one of the two.
  3. One structural nuance: a fully-closed file (archived project, zero open eras) can only pass staleness if the template derives nothing. Archived projects whose template still derives an entry (arenaz) therefore stay on nonTemplateDaTracking until an “archived” affordance exists.
migration of the 20 override projects into era files is the designated follow-up — see /tmp/handoff-datracking-migration.md
F9

Rotation attempted the old way — defense in depth

trigger: someone edits identities by hand / deletes an era / bypasses da:history
  1. Hand-edited file violating an invariant → config build throws (parser, §4).
  2. Era deleted or identity mutated in place → snapshot guard: “identities disappeared … must be addressed by a human” — now with the extra hint to run da:history instead of signing off a removal.
  3. Same wipe about to ship anyway → pnpm da:preview prints the identity diff with the same warning before deploy.
three independent tripwires; the AI-facing message in the snapshot guard still says: hand removals to a human
§6

Boundary semantics — the bracket

Nobody knows the exact rotation block at generation time — only that it happened between two discovery runs. The generator doesn't guess; it brackets:

precisionboundary comes fromwhen
bracketedtimestamp→block over RPC for main's and the local discovered.json timestamps (interpolating binary search, getBlockNumberAtOrBefore)default for ethereum/ethereum eras
manual--since-block / --until-block flagscelestia · avail · no RPC · no main ref
exactreserved — a future --exact mode scanning rotation events (SystemConfig.ConfigUpdate etc.) to shrink the bracket to zero widthfollow-up
Known edge

The bracket's lower bound is main's run timestamp. If main already holds the rotated value (someone merged a discovery refresh past a red guard and healed later), the lower bound sits after the true rotation and the gap is invisible to the tool — that's the one case to bracket by hand with --since-block further back.

§7

The guard rails — every CI check

Two independent test families, both in pnpm test (packages/config), plus build-time parsing. What each failure means and its fix:

checkfails whenfix
history · staleness
history.test.ts		 a file's open-era identity set ≠ the current template derivation's identity set (rotation F3, flap F4, layer switch F6) pnpm da:history <project> (or --drop-last for a flap)
history · file required a template project derives tracking but has no daTracking.json (new project F1) pnpm da:history <project> — init
history · orphans a daTracking.json exists that no template reads (override also set, or project renamed/removed) delete the file or the override — never keep both
parser invariants
build-time throw		 hand edit or generator bug produced an illegal era list (I1–I5, §4) regenerate; don't hand-edit
snapshot · disappeared
guard.test.ts		 any production id (all 202+, template or not, incl. sovereign configs) vanished from the built config human decision; hint now points to da:history for template rotations. Removal sign-off = pnpm snapshots:generate
snapshot · stale new ids exist that aren't registered yet pnpm snapshots:generate (auto-run by da:history)
snapshot · duplicates two configs anywhere hash to one id discriminator (template path) or fix the config

The two families are deliberately redundant: the history guard understands intent (what should the open era be?), the snapshot guard understands consequence (which ids does production depend on?). The history file is the record; the snapshot is the tripwire — it also covers everything the era ledger doesn't (overrides, sovereign configs, eigen-da).
